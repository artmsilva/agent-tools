# Apple `container` boundary spike — 2026-07-26

## Question

Can `pi-drydock` run an unprivileged task in an Apple container without mounting the host workspace, block external egress, preserve the original source, and return an applicable patch?

## Environment

- macOS 26.5.2 (`arm64`)
- Apple `container` 1.1.0, signed and notarized installer
- Recommended Kata 3.28.0 kernel
- Alpine 3.23 image index pinned to `sha256:fd791d74b68913cbb027c6546007b3f0d3bc45125f797758156952bc2d6daf40`

## Result

**Passed.** Run [`../scripts/spike.sh`](../scripts/spike.sh) to reproduce.

| Boundary check | Result |
|---|---|
| Guest process runs as UID/GID 65534 | Pass |
| Host `/Users` tree is absent | Pass |
| Root filesystem rejects writes, including UID 0 | Pass |
| Workspace and `/tmp` are writable tmpfs mounts | Pass |
| All Linux capabilities are dropped | Pass |
| Direct request to `1.1.1.1` fails on an internal, no-DNS network | Pass |
| Original host source hash remains unchanged | Pass |
| Exported unified patch applies to a host-side copy | Pass |

Exported patch:

```diff
--- message.txt
+++ message.txt
@@ -1 +1 @@
-status=original
+status=edited-in-guest
```

## Findings

1. **The secure launch flags compose cleanly.** `--uid 65534 --gid 65534 --cap-drop ALL --read-only --tmpfs /tmp --tmpfs /workspace --network <internal> --no-dns` produced the intended baseline with 1 CPU and 512 MB RAM.
2. **Copy-in must target the live mount.** `container copy` reported success but wrote beneath the running tmpfs mount, so the guest could not see the file. Streaming through `container exec --interactive ... 'cat > /workspace/file'` reached the live tmpfs. Export used the inverse `container exec ... cat` stream.
3. **Dropping capabilities is observable.** UID 0 could not `chown` after `--cap-drop ALL`; the file therefore enters as the final unprivileged UID rather than being copied as root and fixed later.
4. **No live host mount is required.** The source file was streamed in, edited only in guest tmpfs, and returned as a patch. The host original retained the same SHA-256.
5. **The network result is narrow.** This proves the test container could not reach the external IP. It does not prove host-gateway isolation; Apple issue [#1320](https://github.com/apple/container/issues/1320) remains a separate threat to test and mitigate.

## Decision

The first `DrydockController` should use exec streams for copy-in/export, not `container copy` or a read-write host bind mount. Keep the image pinned, run as the final unprivileged UID from the first write, and preserve the internal-network regression check.

This spike does **not** yet route Pi tools, test host-gateway access, broker approved egress, or exercise Davit.
